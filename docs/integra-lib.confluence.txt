Библиотека общих компонентов, не зависящих от архитектуры. Заголовочная (кроме одного компонента), C++20, без исключений и RTTI.

Каждый компонент — отдельный репозиторий со своей версией. Проект подключает сабмодулем только те, которыми пользуется, и обновляет их независимо друг от друга.

Сейчас репозитории живут в организации [integra-lib на GitHub|https://github.com/integra-lib] как на временной площадке; планируется переезд в группу GitLab {{internal-projects/integra-lib}}. При переезде изменится только URL в {{.gitmodules}} потребителя.

h2. Обзор

|| Репозиторий || Что даёт || Когда нужен ||

{{transaction_engine}} поставляется одним неделимым компонентом: отправитель, приёмник и формат кадра осмысленны только в одной и той же версии друг друга, поэтому это одна цель с одним зонтичным заголовком.

h2. Компоненты

h3. Структуры данных (Data Structures)

h4. ring-buffer

{{integra::RingBuffer<T, SIZE>}} — кольцевой буфер фиксированного размера поверх {{std::array}}. Память не выделяет, размер задаётся шаблонным параметром. При заполнении новое значение отбрасывается. Методы: {{Push}}, {{Pop}}, {{Clear}}, {{IsEmpty}}.

{code:language=cpp}
#include <integra/ring_buffer.hpp>
integra::RingBuffer<std::uint16_t, 32> samples;
samples.Push(value);
std::uint16_t out{};
if (samples.Pop(out))
{
    Process(out);
}
{code}

h4. const-map

{{integra::ConstMap<Key, Value, SIZE>}} — таблица «ключ — значение», задаваемая на этапе компиляции. Поиск линейный, поэтому компонент предназначен для небольших таблиц. Отсутствие ключа — не ошибка, а {{std::nullopt}}.

{code:language=cpp}
#include <integra/const_map.hpp>
constexpr integra::ConstMap<Code, std::string_view, 3> NAMES{{{
    {Code::eOk,      "ok"},
    {Code::eTimeout, "timeout"},
    {Code::eCrc,     "crc"},
}}};
if (const auto name = NAMES.Find(code); name.has_value())
{
    Print(name.value());
}
{code}

h4. dedup-cache

{{integra::DedupCache<CAPACITY>}} — кольцевой кеш последних увиденных идентификаторов фиксированной ёмкости. Память не выделяет; при переполнении вытесняется самый старый. Нужен там, где повтор сообщения надо отличить от нового.

{code:language=cpp}
#include <integra/dedup_cache.hpp>
integra::DedupCache<16> seen;
if (!seen.Contains(messageId))
{
    Handle(message);
    seen.Insert(messageId);
}
{code}

h3. Утилиты (Utilities)

h4. function

{{integra::Function<R(Args...)>}} — облегчённый аналог {{std::function}}: хранит любой вызываемый объект с заданной сигнатурой. Копирование запрещено, перемещение разрешено. Вызываемый объект размещается в куче, поэтому в контексте без динамической памяти компонент неприменим.

{code:language=cpp}
#include <integra/function.hpp>
integra::Function<void(int)> handler = [](int code) { Handle(code); };
handler(42);
if (handler)
{
    // проверка на пустоту
}
{code}

h4. bit-ops

Сборка и разбор беззнаковых целых по байтам. Всё {{constexpr}}, вычисляется на этапе компиляции. Типы проверяются: только беззнаковые целые, число байтов не превышает размер результата.

{code:language=cpp}
#include <integra/bit_ops.hpp>
// собрать целое из байтов, младший первым
constexpr auto word = integra::AssembleBytes<std::uint16_t>(0x12U, 0x34U); // 0x3412
// извлечь байт по индексу, 0 — младший
constexpr auto lsb = integra::GetByteByIndex<0>(0xABCDU); // 0xCD
{code}

h4. enum-utils

{{integra::EnumValue}} — преобразует элемент перечисления в его числовое значение, сохраняя базовый тип.

{code:language=cpp}
#include <integra/enum_utils.hpp>
const auto raw = integra::EnumValue(Command::eReset);
{code}

h4. hex-string

Перевод шестнадцатеричного текста в байты и обратно — в буфер вызывающего, без динамической памяти и без исключений, всё {{constexpr}}.

{{BytesToHex}} пишет hex в нижнем регистре, по два символа на байт, ведущий ноль включён. {{BytesToHexReversed}} — то же, но начиная с младшего байта: так печатается MAC, который радио отдаёт в порядке передачи по эфиру, обратном порядку записи. {{HexToBytes}} разбирает строку обратно в байты.

Обе стороны возвращают {{std::optional}} с числом записанных элементов. Нечётная длина, символ не из набора и не влезающий буфер — это значение, а не исключение: строка обычно пришла из канала, где «неправильная» — обычное дело, а библиотека собирается с выключенными исключениями. Пока не разобран весь вход, в буфер не пишется ничего, поэтому вызывающий, проигнорировавший результат, не увидит половину значения.

{{HexCharCount(n)}} даёт нужный размер буфера под форматирование; массив на единицу больше, инициализированный нулями, заодно оказывается C-строкой.

{code:language=cpp}
#include <integra/hex_string.hpp>

std::array<char, integra::HexCharCount(sizeof(mac)) + 1U> text{};
if (integra::BytesToHexReversed(mac, text).has_value())
{
    LOG_INF("peer %s", text.data());
}

std::array<std::uint8_t, 6> parsed{};
const auto count = integra::HexToBytes(text.data(), parsed);
if (!count.has_value())
{
    return Reject();
}
{code}

h3. Алгоритмы (Algorithms)

h4. ema-filter

{{integra::EmaFilter}} — экспоненциальное скользящее среднее. Первое измерение принимается без запаздывания: {{Update()}} сразу возвращает поданное значение, а не ползёт к нему от нуля. {{Reset()}} возвращает фильтр в это состояние.

{code:language=cpp}
#include <integra/ema_filter.hpp>
integra::EmaFilter filter{0.25F};
const float smoothed = filter.Update(rawVoltage);
{code}

h4. crc

Три контрольные суммы, названные по каталогу алгоритмов, — чтобы из места вызова было видно, какой именно алгоритм используется, без чтения реализации. Побитовые, без таблиц: таблица во флеше ради суммы, считаемой один раз при загрузке, не окупается. Все три {{constexpr}}.

* {{Crc8Nrsc5}} — полином 0x31, начальное значение 0xFF. Датчики Sensirion (SHT4x и родственные).
* {{Crc16Ccitt}} — полином 0x1021, начальное значение 0xFFFF. Вариант CCITT-FALSE.
* {{Crc32IsoHdlc}} — отражённый полином 0xEDB88320. Тот же, что в zlib, Ethernet и PNG.
* {{Crc32Stream}} — инкрементальная форма CRC-32 для данных, приходящих частями: проверка образа прошивки постранично.

{code:language=cpp}
#include <integra/crc.hpp>
const std::uint16_t frameCrc = integra::Crc16Ccitt(frameBytes);

integra::Crc32Stream image;
for (const auto& page : pages)
{
    image.Update(page);
}
const bool valid = image.Value() == expectedCrc;
{code}

h3. Исполнение (Execution)

h4. work-queue

{{integra::IWorkQueue}} — интерфейс отложенного выполнения: обработчик запускается позже, в том контексте, которым владеет реализация. Реализации платформенные и живут в проекте, библиотека даёт только контракт.

{code:language=cpp}
#include <integra/work_queue.hpp>
void Setup(integra::IWorkQueue& queue)
{
    queue.SetHandler([] { DoDeferredWork(); });
    queue.Submit();
}
{code}

h4. periodic-clock

{{integra::IPeriodicClock}} — интерфейс монотонных часов и периодического тика. Отделяет две единственные аппаратные зависимости адаптерного слоя, благодаря чему код над ним тестируется на хосте с подставной реализацией.

{code:language=cpp}
#include <integra/periodic_clock.hpp>
clock.StartTick(std::chrono::milliseconds{100}, [] { engine.OnTick(); });
{code}

h3. События (Events)

h4. event-manager

{{integra::EventManager<Payload, Queue, MaxSubscriptions>}} — публикация и подписка поверх очереди. Обработчики регистрируются по идентификатору события, доставка идёт в том контексте, который вызвал {{Dispatch()}} (блокирующий) или {{TryDispatch()}} (неблокирующий, для потребителей со своим циклом).

Очередь компоненту не принадлежит, её даёт потребитель: на устройстве это примитив RTOS, в тестах — массив. Реализация удовлетворяет концепту {{integra::EventQueueLike}} — {{TryPush}} (не блокирует, вызывается из прерывания), {{TryPop}}, {{PopBlocking}}. Требование trivially copyable payload принадлежит очереди, которая копирует событие побайтно, а не самому компоненту.

Время передаётся снаружи параметром {{nowMs}}, часов компонент не читает. Переполнение таблицы подписок и переполнение очереди не пишутся в лог, а сообщаются колбэками: компонент, который логирует, вынужден выбрать backend и перестаёт быть независимым от платформы. Отчёт о потерянных событиях копит счётчик и выдаётся не чаще одного раза в {{QUEUE_FULL_REPORT_PERIOD_MS}} — знать о потерях надо, знать о каждой в отдельности не надо, а незадросселированный отчёт замедляет и без того отстающий цикл.

{code:language=cpp}
#include <integra/event_manager.hpp>

MsgqEventQueue<AppPayload, 8> queue;              // адаптер проекта поверх k_msgq
integra::EventManager<AppPayload, decltype(queue)> events{ queue };

events.Subscribe(AppEvent::eTick, [](const AppPayload& payload) { OnTick(payload); });
events.SetOnEventsDropped([](std::uint8_t id, std::uint32_t dropped) {
    LOG_WRN("queue full, %u dropped (last id=%u)", dropped, id);
});

std::ignore = events.Push(AppEvent::eTick, payload, k_uptime_get_32());
while (events.TryDispatch()) {}
{code}

h4. button-event

{{integra::ButtonEventCore}} — антидребезг одной кнопки и разбор нажатия: короткое, длинное или слишком короткое, чтобы что-то значить. Пин, таймеры и часы снаружи: ядро получает фронт с пина, уровень, снятый после выдержки, и срабатывание длинного таймаута, а возвращает {{ButtonAction}} — что сделать с таймерами. Возврат помечен атрибутом {{nodiscard}}: проигнорированный {{ButtonAction}} — это незаведённый таймер, то есть кнопка, которая молчит.

Три времени задают смысл нажатия. Фронт опрашивается один раз, после {{confirmMs}} тишины на линии. Подтверждённое нажатие короче {{minPressMs}} — это касание, а не решение, и оно не сообщается вовсе. Нажатие, всё ещё удерживаемое через {{longPressMs}}, — длинное, и на отпускании оно не сообщается ещё раз как короткое: одно нажатие — одно решение. Без колбэка длинного нажатия таймер не заводится совсем.

Все три входа должны вызываться из одного контекста. На устройстве и фронт с пина, и длинный таймаут приходят в прерывании, поэтому адаптер откладывает их в очередь работ, а не зовёт напрямую, — именно это позволяет держать состояние обычными {{bool}} и делать в колбэках настоящую работу.

{code:language=cpp}
#include <integra/button_event.hpp>

integra::ButtonEventCore button{ { .confirmMs = 20, .minPressMs = 200, .longPressMs = 1000 } };
button.SetOnShortPress([] { ToggleView(); });
button.SetOnLongPress([] { EnterService(); });

// в адаптере проекта:
Apply(button.OnEdge());                             // из ISR — только перезапуск выдержки
Apply(button.OnConfirmed(pin.Get(), k_uptime_get())); // из очереди работ
Apply(button.OnLongPressElapsed(pin.Get()));          // из очереди работ
{code}

h3. Хранение (Persistence)

h4. settings-record

Запись настроек с контрольной суммой: {{WriteSettingsRecord}} кладёт в хранилище payload вместе с CRC-32, {{ReadSettingsRecord}} отдаёт его обратно, только если сумма сошлась, и не трогает переданную переменную, если нет, — значение по умолчанию переживает и первую загрузку, и испорченную ячейку.

Хранилище даёт потребитель: на устройстве это NVS или драйвер EEPROM, в тестах — словарь. Оно удовлетворяет концепту {{integra::RecordStorageLike}} — {{Write}} и {{Read}} поверх {{std::span}}. Имя раздела и флеш-устройство остаются в проекте, в библиотеку переходит только формат записи.

Зачем сумма: хранилище — не канал. Недописанная после пропадания питания запись или деградировавшая ячейка читаются как правдоподобное значение нужного размера, само чтение при этом не падает. Контрольная сумма — единственное, что отличает это от настройки, которую устройство действительно сохранило.

Payload хранится сырыми байтами, поэтому обязан быть trivially copyable — это {{static_assert}}, а не комментарий.

Зависит от компонента {{crc}}.

{code:language=cpp}
#include <integra/settings_record.hpp>

struct Calibration
{
    std::uint32_t offset{};
    float scale{};
};

if (!integra::WriteSettingsRecord(storage, CALIBRATION_ID, calibration))
{
    LOG_ERR("calibration not saved");
}

Calibration calibration{ DEFAULT_CALIBRATION };
std::ignore = integra::ReadSettingsRecord(storage, CALIBRATION_ID, calibration);
{code}

h3. Связь (Communication)

h4. transaction-engine

Транзакционный протокол поверх ненадёжного канала: отправка с подтверждением, повторы с экспоненциальным backoff, дедупликация на приёме. Поставляется одним компонентом — части протокола версионируются вместе.

{code:language=cpp}
#include <integra/transaction_engine.hpp>
{code}

h5. Формат кадра

{{integra::TransactionFrame}}: идентификатор транзакции, тип, метка времени, полезная нагрузка до 64 байт, контрольная сумма CRC-16/CCITT-FALSE из компонента {{crc}}. {{EncodeTransactionFrame}} возвращает число записанных байт либо 0, если нагрузка велика или буфер мал. {{DecodeTransactionFrame}} возвращает {{false}} при несовпадении суммы, обрезанном кадре или несогласованной длине.

h5. Канал

{{integra::ITransactionTransport}} — интерфейс, через который протокол отправляет и принимает сырые байты. Что под ним — Zigbee, BLE, UART — протокол не знает. Отправитель и приёмник регистрируют обработчики по отдельности, и каждый принятый кадр доставляется обоим: демультиплексирование не нужно, потому что каждая сторона игнорирует чужие кадры.

h5. Отправитель

{{integra::ReliableEventSenderCore<MAX_IN_FLIGHT>}} — назначает идентификатор транзакции, ждёт подтверждения, повторяет с экспоненциальным backoff, паркует отправку, пока канал недоступен, и сообщает об окончательной неудаче.

Время передаётся снаружи параметром {{nowMs}}, а не читается внутри, поэтому машина состояний тестируется на хосте с поддельными часами. Число попыток включает первую отправку: при {{maxRetry = 4}} уходит ровно четыре кадра, а не пять.

{code:language=cpp}
integra::ReliableEventSenderCore<2> sender{deviceId, sendFn};
sender.SetOnConfirmed([](std::uint32_t txnId) { MarkDone(txnId); });
sender.SetOnFailed([](std::uint32_t txnId) { MarkFailed(txnId); });
const auto txnId = sender.Submit(commandType, payload, nowMs);
{code}

h5. Приёмник

{{integra::ReliableEventReceiverCore<DEDUP_CAPACITY>}} — проверяет кадр, отбрасывает повтор уже обработанной транзакции, передаёт новую в обработчик и всегда отвечает подтверждением с тем же идентификатором. Повтор подтверждается, но второй раз не обрабатывается: иначе потерянное подтверждение приводило бы к двойному выполнению команды.

{code:language=cpp}
integra::ReliableEventReceiverCore<16> receiver{handlerFn, sendAckFn};
receiver.OnFrameReceived(rawBytes);
{code}

h2. Подключение к проекту

h3. 1. Добавить нужные компоненты сабмодулями

Подключается только то, чем пользуетесь: неиспользуемые компоненты не скачиваются вовсе.

{code:language=bash}
git submodule add git@github.com:integra-lib/crc.git external/integra/crc
git commit -m "build: add integra-lib crc component"
{code}

h3. 2. Подключить в CMake

{code:language=cmake}
add_subdirectory(external/integra/crc)
target_link_libraries(app PRIVATE Integra::crc)
{code}

Каждый компонент несёт свой каталог включений, поэтому заголовок недоступен, пока компонент не слинкован: забытая зависимость даёт ошибку компиляции, а не случайно работающую сборку.

h3. 3. Включить заголовок

{code:language=cpp}
#include <integra/crc.hpp>
{code}

h3. Компонент с зависимостями

Зависимости есть у двух компонентов: {{transaction-engine}} нужны {{crc}}, {{bit-ops}} и {{dedup-cache}}, а {{settings-record}} — {{crc}}. Они подключаются *рядом* с зависимым компонентом, а не внутрь него, — тогда в дереве проекта каждый компонент существует ровно в одном экземпляре и две разные версии одного компонента в одну прошивку попасть не могут.

{code:language=cmake}
add_subdirectory(external/integra/crc)
add_subdirectory(external/integra/bit-ops)
add_subdirectory(external/integra/dedup-cache)
add_subdirectory(external/integra/transaction-engine)
{code}

Если компонента нет или его версия вне допустимого диапазона, CMake останавливается на configure с сообщением, в котором названы и компонент, и найденная версия:

{noformat}
transaction_engine needs Integra::crc >= 0.1.0 and < 0.2.0, found 0.2.0.
{noformat}

h3. Версии

Каждый компонент выпускается независимо и помечается тегом {{vX.Y.Z}}. До версии 1.0 minor-релиз может ломать API — поэтому зависимые компоненты принимают ровно один minor.

{code:language=bash}
git -C external/integra/crc fetch --tags
git -C external/integra/crc checkout v0.2.0
git add external/integra/crc
git commit -m "build: bump crc to v0.2.0"
{code}

Обновление версии — обычное изменение в истории проекта: видно в diff, проходит ревью, откатывается коммитом.

h3. Что учесть в CI потребителя

Компоненты — обычные сабмодули, поэтому сборочным job'ам нужен {{GIT_SUBMODULE_STRATEGY: normal}} (или {{recursive}}). Частая ошибка: переменная выставлена только у job'а с unit-тестами, а сборка прошивки падает на отсутствующем каталоге.

h3. Требования

* C++20
* исключения и RTTI библиотека не использует и не требует
* динамическая память нужна компоненту {{function}}, а также обработчикам {{event-manager}} и колбэкам {{button-event}}: они хранятся в {{std::function}}, которая выделяет память под достаточно большой захват. Регистрируются они один раз при старте, но в контексте, где куча запрещена вовсе, это надо учитывать
* {{transaction-engine}} — единственный компонент со своей единицей трансляции, то есть статическая библиотека. Под Zephyr такой библиотеке нужно передать флаги SDK, иначе она соберётся с другим ABI, чем приложение. Перед использованием в прошивке это надо проверить на реальном тулчейне; заголовочных компонентов это не касается — они компилируются в составе приложения.

Собственные тесты компонентов собираются, только когда репозиторий компонента открыт как корневой проект. В сборке потребителя они не участвуют, GoogleTest не скачивается.
