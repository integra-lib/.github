hwlib — библиотека общих компонентов, не зависящих от архитектуры. Компоненты на C++20, заголовочные (кроме {{transaction-engine}} и адаптера {{zigbee-app}}), без исключений и RTTI. Исключение — {{boot-slots}}: он на C (C11) с C API, потому что бутлоадеры часто пишутся на C. И {{zigbee-app}} — единственный компонент, привязанный к платформе: его адаптер вызывает ZBOSS и собирается только в приложении nRF Connect SDK; решения, которые он исполняет, вынесены в заголовки без ZBOSS и проверены тестами на хосте.

Каждый компонент — отдельный репозиторий со своей версией. Проект подключает сабмодулем только те, которыми пользуется, и обновляет их независимо друг от друга.

Репозитории опубликованы в организации [integra-lib на GitHub|https://github.com/integra-lib]. GitLab-зеркала размещаются в группе {{internal-projects/a000-hwlib}} и её разделах. При смене хоста изменится только URL в {{.gitmodules}} потребителя.

h2. Обзор

Проекты в описании — это где работал исходный код, из которого сделан компонент. Сами версии компонентов hwlib на железе ещё не запускались: они не зависят от МК, собираются любым тулчейном C++20 ({{boot-slots}} — C11) и проверены тестами на хосте. Адаптер {{zigbee-app}} собран в образе nRF Connect SDK, но не слинкован в прошивку и не запускался.

h2. Компоненты

h3. Структуры данных ({{data_structures}})

h4. ring-buffer

{{hwlib::data_structures::RingBuffer<T, SIZE>}} — кольцевой буфер фиксированного размера поверх {{std::array}}. Память не выделяет, размер задаётся шаблонным параметром. При заполнении новое значение отбрасывается. Методы: {{Push}}, {{Pop}}, {{Clear}}, {{IsEmpty}}.

{code:language=cpp}
#include <hwlib/data_structures/ring_buffer.hpp>
hwlib::data_structures::RingBuffer<std::uint16_t, 32> samples;
samples.Push(value);
std::uint16_t out{};
if (samples.Pop(out))
{
    Process(out);
}
{code}

h4. const-map

{{hwlib::data_structures::ConstMap<Key, Value, SIZE>}} — таблица «ключ — значение», задаваемая на этапе компиляции. Поиск линейный, поэтому компонент предназначен для небольших таблиц. Отсутствие ключа — не ошибка, а {{std::nullopt}}.

{code:language=cpp}
#include <hwlib/data_structures/const_map.hpp>
constexpr hwlib::data_structures::ConstMap<Code, std::string_view, 3> NAMES{{{
    {Code::eOk,      "ok"},
    {Code::eTimeout, "timeout"},
    {Code::eCrc,     "crc"},
}}};
if (const auto name = NAMES.Find(code); name.has_value())
{
    Print(name.value());
}
{code}

h4. dedup-cache

{{hwlib::data_structures::DedupCache<CAPACITY>}} — кольцевой кеш последних увиденных идентификаторов фиксированной ёмкости. Память не выделяет; при переполнении вытесняется самый старый. Нужен там, где повтор сообщения надо отличить от нового.

{code:language=cpp}
#include <hwlib/data_structures/dedup_cache.hpp>
hwlib::data_structures::DedupCache<16> seen;
if (!seen.Contains(messageId))
{
    Handle(message);
    seen.Insert(messageId);
}
{code}

h3. Утилиты ({{utilities}})

h4. function

{{hwlib::utilities::Function<R(Args...)>}} — облегчённый аналог {{std::function}}: хранит любой вызываемый объект с заданной сигнатурой. Копирование запрещено, перемещение разрешено. Вызываемый объект размещается в куче, поэтому в контексте без динамической памяти компонент неприменим.

{code:language=cpp}
#include <hwlib/utilities/function.hpp>
hwlib::utilities::Function<void(int)> handler = [](int code) { Handle(code); };
handler(42);
if (handler)
{
    // проверка на пустоту
}
{code}

h4. bit-ops

Сборка и разбор беззнаковых целых по байтам. Всё {{constexpr}}, вычисляется на этапе компиляции. Типы проверяются: только беззнаковые целые, число байтов не превышает размер результата.

{code:language=cpp}
#include <hwlib/utilities/bit_ops.hpp>
// собрать целое из байтов, младший первым
constexpr auto word = hwlib::utilities::AssembleBytes<std::uint16_t>(0x12U, 0x34U); // 0x3412
// извлечь байт по индексу, 0 — младший
constexpr auto lsb = hwlib::utilities::GetByteByIndex<0>(0xABCDU); // 0xCD
{code}

h4. enum-utils

{{hwlib::utilities::EnumValue}} — преобразует элемент перечисления в его числовое значение, сохраняя базовый тип.

{code:language=cpp}
#include <hwlib/utilities/enum_utils.hpp>
const auto raw = hwlib::utilities::EnumValue(Command::eReset);
{code}

h4. hex-string

Перевод шестнадцатеричного текста в байты и обратно — в буфер вызывающего, без динамической памяти и без исключений, всё {{constexpr}}.

{{BytesToHex}} пишет hex в нижнем регистре, по два символа на байт, ведущий ноль включён. {{BytesToHexReversed}} — то же, но начиная с младшего байта: так печатается MAC, который радио отдаёт в порядке передачи по эфиру, обратном порядку записи. {{HexToBytes}} разбирает строку обратно в байты.

Обе стороны возвращают {{std::optional}} с числом записанных элементов. Нечётная длина, символ не из набора и не влезающий буфер — это значение, а не исключение: строка обычно пришла из канала, где «неправильная» — обычное дело, а библиотека собирается с выключенными исключениями. Пока не разобран весь вход, в буфер не пишется ничего, поэтому вызывающий, проигнорировавший результат, не увидит половину значения.

{{HexCharCount(n)}} даёт нужный размер буфера под форматирование; массив на единицу больше, инициализированный нулями, заодно оказывается C-строкой.

{code:language=cpp}
#include <hwlib/utilities/hex_string.hpp>

std::array<char, hwlib::utilities::HexCharCount(sizeof(mac)) + 1U> text{};
if (hwlib::utilities::BytesToHexReversed(mac, text).has_value())
{
    LOG_INF("peer %s", text.data());
}

std::array<std::uint8_t, 6> parsed{};
const auto count = hwlib::utilities::HexToBytes(text.data(), parsed);
if (!count.has_value())
{
    return Reject();
}
{code}

h4. byte-codec

Кодирует целые числа, enum и float в big- или little-endian байты. {{Store}} и {{Load}} работают со значением фиксированного размера; {{ByteReader}} читает поля пакета по порядку из заимствованного буфера. Ошибка короткого чтения становится sticky, а чтение массива выполняется целиком или не меняет его.

{code:language=cpp}
#include <hwlib/utilities/byte_codec.hpp>

const auto bytes = hwlib::utilities::Store<std::endian::big>(std::uint32_t{0x12345678U});
const auto value = hwlib::utilities::Load<std::endian::big, std::uint32_t>(std::span{bytes});

hwlib::utilities::ByteReader<std::endian::little, std::byte> reader{payload};
reader >> vendor >> name >> version;
if (reader.Failed())
{
    // короткий пакет: непрочитанное поле и курсор не меняются
}
{code}

h3. Алгоритмы ({{algorithms}})

h4. ema-filter

{{hwlib::algorithms::EmaFilter}} — экспоненциальное скользящее среднее. Первое измерение принимается без запаздывания: {{Update()}} сразу возвращает поданное значение, а не ползёт к нему от нуля. {{Reset()}} возвращает фильтр в это состояние.

{code:language=cpp}
#include <hwlib/algorithms/ema_filter.hpp>
hwlib::algorithms::EmaFilter filter{0.25F};
const float smoothed = filter.Update(rawVoltage);
{code}

h4. crc

Три контрольные суммы, названные по каталогу алгоритмов, — чтобы из места вызова было видно, какой именно алгоритм используется, без чтения реализации. Побитовые, без таблиц: таблица во флеше ради суммы, считаемой один раз при загрузке, не окупается. Все три {{constexpr}}.

* {{Crc8Nrsc5}} — полином 0x31, начальное значение 0xFF. Датчики Sensirion (SHT4x и родственные).
* {{Crc16Ccitt}} — полином 0x1021, начальное значение 0xFFFF. Вариант CCITT-FALSE.
* {{Crc32IsoHdlc}} — отражённый полином 0xEDB88320. Тот же, что в zlib, Ethernet и PNG.
* {{Crc32Stream}} — инкрементальная форма CRC-32 для данных, приходящих частями: проверка образа прошивки постранично.

{code:language=cpp}
#include <hwlib/algorithms/crc.hpp>
const std::uint16_t frameCrc = hwlib::algorithms::Crc16Ccitt(frameBytes);

hwlib::algorithms::Crc32Stream image;
for (const auto& page : pages)
{
    image.Update(page);
}
const bool valid = image.Value() == expectedCrc;
{code}

h4. debouncer

{{hwlib::algorithms::Debouncer<INC, DEC>}} — антидребезг по числу отсчётов. Насыщающийся счётчик растёт на {{INC}} с каждым истинным отсчётом и уменьшается на {{DEC}} с каждым ложным; состояние «установлен» держится, пока счётчик стоит на пороге.

Он несимметричен, и это его назначение, а не упущение: установиться ему нужно {{threshold / INC}} согласных отсчётов, а сброситься при {{DEC}}, равном {{INC}}, — одного несогласного. Он подтверждает условие, прежде чем на него реагировать, и отпускает, как только условие нарушено. Если сброс тоже должен сопротивляться, нужен гистерезис — это не он. Шаги взвешивают свидетельства: {{Debouncer<1, 3>}} устанавливается медленно, а сбрасывается втрое быстрее.

Считает отсчёты, а не время. Для кнопки на пине, где важно время установления, есть {{button-event}}.

{code:language=cpp}
#include <hwlib/algorithms/debouncer.hpp>

hwlib::algorithms::Debouncer<> overLimit{ 5U };   // пять превышений подряд, прежде чем поднять тревогу
if (overLimit.Update(reading > LIMIT))
{
    RaiseAlarm();
}
{code}

h4. filters

Три фильтра для показаний датчиков. Память фиксированная, без выделения, без исключений, всё {{constexpr}}; каждый возвращает {{std::optional}} — до первого отсчёта «ничего», а не ноль, похожий на измерение.

* {{MedianFilter<T, CAPACITY>}} — скользящая медиана. Для показания, которое в основном верное и изредка дико неверное: один выброс в окне не сдвигает результат вовсе. Работает и скользящим окном, и пачками ({{IsFull()}}, прочитать, {{Clear()}}); окно можно сузить на ходу через {{SetWindow()}}, и тогда фильтр начинает заново. При чётном числе отсчётов результат — середина двух средних через {{std::midpoint}}, без переполнения у границы типа.
* {{HysteresisFilter<T, N>}} — триггер Шмитта на N порогах. Для показания, которое определяет состояние: колебания у порога не переключают его на каждом отсчёте. Внутри состояния значение отслеживается свободно; переход засчитывается, только когда отсчёт ушёл за ближайший порог дальше полосы.
* {{MovingAverage<T, N>}} — скользящее среднее. Сумма целых хранится в 64 битах, сумма с плавающей точкой пересчитывается из окна раз за круг, а пока окно не заполнено, среднее берётся по уже полученным отсчётам.

{code:language=cpp}
#include <hwlib/algorithms/filters.hpp>

hwlib::algorithms::MedianFilter<std::uint32_t, 15> voltage{ 5U };
hwlib::algorithms::HysteresisFilter status{ std::array{ LOW_MV, STANDBY_MV, GOOD_MV }, BAND_MV };
hwlib::algorithms::MovingAverage<float, 4> current;

voltage.Push(sample);
if (const auto mv = voltage.Value(); mv.has_value())
{
    status.Push(mv.value());
}
{code}

h4. battery-monitor

{{hwlib::algorithms::BatteryMonitor<Gauge>}} — степень заряда (SoC) батареи по кулоновскому счётчику. При холодном старте SoC оценивается по напряжению холостого хода (OCV = V − I·R по замеру под нагрузкой) и таблице OCV → SoC, дальше считается по счётчику. Смещение заряда хранится в RAM счётчика вместе с инвертированной копией, поэтому после сброса МК счёт продолжается, а не угадывается заново; сохранённое состояние принимается, только если оно близко к оценке по напряжению.

Счётчик — любой тип с методами concept {{CoulombGauge}}; драйвер {{stc3100}} подходит как есть. Коррекции (ниже нуля, выше ёмкости, {{MarkFull()}} по сигналу зарядника) меняют только смещение и сразу его сохраняют; сам счётчик сбрасывается только перед переполнением, и смещение пишется до сброса. Часов внутри нет: {{Update()}} вызывает приложение. Что показывать пользователю (10 % как «пусто», 99 % на зарядке, порог предупреждения) — решение продукта.

{code:language=cpp}
#include <hwlib/algorithms/battery_monitor.hpp>

constexpr std::array OCV{hwlib::algorithms::OcvPoint{3400U, 0.0F}, hwlib::algorithms::OcvPoint{3735U, 0.6F},
                         hwlib::algorithms::OcvPoint{4131U, 1.0F}};
static_assert(hwlib::algorithms::IsValidOcvTable(OCV));

hwlib::algorithms::BatteryMonitor<Gauge> g_battery{g_gauge, OCV, {.capacityUah = 1'800'000, .internalResistanceMilliOhm = 190U}};

std::ignore = g_battery.Start(); // eNotReady, пока счётчик не дал напряжение
std::ignore = g_battery.Update();
const float soc = g_battery.Soc();
{code}

Алгоритм взят из трёх проектов на STC3100 (a156, a159, a160). Исправлено: во всех трёх после коррекции счётчик обнулялся без сохранения нового смещения, и после сброса МК заряд откатывался; смещение было {{int16_t}} (около 6,6 А·ч при шунте 33 мОм); a160 пропускал NaN и SoC выше 1 из RAM; a156 ждал в цикле 3,4 В, которых разряженная батарея не даёт. На устройстве не запускался.

h4. bresenham-modulator

{{hwlib::algorithms::BresenhamModulator}} распределяет {{level}} включений на каждые {{steps}} шагов — алгоритм Брезенхема по одному шагу. Типичное применение — ТЭН через твердотельное реле с переходом через ноль: один шаг на полупериод сети, реле переключает только целые полупериоды, мощность — {{level / steps}}, без долгих пауз медленного ШИМ. При постоянном уровне в любом окне из {{steps}} шагов ровно {{level}} включений, промежутки различаются не больше чем на шаг, счёт отклоняется от идеального не больше чем на полшага. Новый уровень сохраняет накопленную ошибку: частые вызовы {{SetLevel()}} не перезапускают паттерн. {{SetLevel()}} можно вызывать из задачи, а {{Next()}} — из прерывания: общий у них только 16-битный atomic, на Cortex-M0 это обычные загрузка и сохранение.

{code:language=cpp}
hwlib::algorithms::BresenhamModulator g_heater{100};   // 100 полупериодов: уровень = проценты

g_heater.SetLevel(37);                                  // из задачи: ПИД, Modbus
std::ignore = gpio_pin_set_dt(&g_ssr, g_heater.Next() ? 1 : 0);   // в прерывании перехода через ноль
{code}

Взят из a146-control-board ({{heat-ctrl/bresenham.hpp}}). Исправлено: {{SetValue()}} сбрасывал паттерн, и мощность зависела от частоты вызовов — при записи раз в 10 полупериодов 1 % и 5 % давали 0 %, 25 % — 20 %, 37 % — 40 %; задача и прерывание гонялись за три поля; {{GetSize()}} обрезал размер до 8 бит. Состояния старт/стоп/авария и таймер перехода через ноль остались в прошивке платы.

h3. Исполнение ({{execution}})

h4. work-queue

{{hwlib::execution::IWorkQueue}} — интерфейс отложенного выполнения: обработчик запускается позже, в том контексте, которым владеет реализация. Реализации платформенные и живут в проекте, библиотека даёт только контракт.

{code:language=cpp}
#include <hwlib/execution/work_queue.hpp>
void Setup(hwlib::execution::IWorkQueue& queue)
{
    queue.SetHandler([] { DoDeferredWork(); });
    queue.Submit();
}
{code}

h4. periodic-clock

{{hwlib::execution::IPeriodicClock}} — интерфейс монотонных часов и периодического тика. Отделяет две единственные аппаратные зависимости адаптерного слоя, благодаря чему код над ним тестируется на хосте с подставной реализацией.

{code:language=cpp}
#include <hwlib/execution/periodic_clock.hpp>
clock.StartTick(std::chrono::milliseconds{100}, [] { engine.OnTick(); });
{code}

h4. worker

{{hwlib::execution::Worker<Mutex>}} — очередь отложенной работы: любой контекст ставит в неё вызываемый объект, а контекст, которому принадлежит worker, выполняет всё накопленное при вызове {{Update()}} — в порядке постановки.

Мьютекс захватывается только на время работы с очередью, но не на время выполнения работы. Поэтому работа может ставить новую работу — та выполнится в том же {{Update()}}, — а сам worker работает с нерекурсивным мьютексом, каким обычно и бывает мьютекс ядра.

Мьютекс — обязательный параметр шаблона: подходит всё, что умеет {{lock()}}/{{unlock()}}. Значения по умолчанию нет намеренно: {{std::mutex}} есть только там, где у библиотеки C++ есть потоки, — на хосте и в ESP-IDF, но не в Zephyr SDK и не на голом arm-none-eabi. На RTOS это обёртка над мьютексом ядра, в конструкторе которой объект ядра и инициализируется.

Очередь растёт в куче, по одному {{std::function}} на поставленную работу: производитель, обгоняющий {{Update()}}, растит её без ограничения.

{code:language=cpp}
#include <hwlib/execution/worker.hpp>

hwlib::execution::Worker<ZephyrMutex> worker;   // или Worker<std::mutex>, где он есть
worker.Post([this] { OnStopped(); });   // из любого контекста
worker.Update();                        // в главном цикле: выполнить всё накопленное
{code}

h4. coro

Корутины C++20 для прошивок, пространство имён {{hwlib::execution}}. {{Task<T>}} — ленивая задача: выполняется, когда её ждут через {{co_await}} или запускают {{Resume()}}; {{SyncWait}} выполняет её из обычного кода, блокируясь на событии ({{Set()}}/{{Wait()}}); {{WhenAllReady}} ждёт несколько сразу; {{AsyncScope}} запускает работу «в фон» и ждёт её в {{Join()}}; {{AsyncGenerator}} отдаёт поток значений.

{{IoService<Semaphore, Clock>}} — планировщик с таймерами, который обслуживает один поток: {{co_await io.Schedule()}} переносит корутину на этот поток, {{co_await io.ScheduleAfter(500ms)}} — через заданное время. Планировать можно из любого потока, без блокировок и без выделения памяти: каждая ожидающая корутина — узел интрузивного списка в собственном кадре. Семафор и часы — параметры шаблона, часы обязаны быть монотонными. {{Run()}} работает раундами, поэтому непрерывная нагрузка не мешает таймерам и остановке. Очереди {{SpscQueue}} и {{MpmcQueue}} ограниченного размера; {{MpmcQueue}} никогда не ждёт и годится для прерываний.

{code:language=cpp}
#include <hwlib/execution/coro.hpp>

using namespace hwlib::execution;

IoService<KernelSemaphore, UptimeClock> g_io; // k_sem и k_uptime_get() за двумя обёртками

Task<int> ReadTemperature()
{
    co_await g_io.ScheduleAfter(std::chrono::milliseconds{10}); // время преобразования
    co_return 21;
}

Task<int> ReadBoth()
{
    auto [t, h] = co_await WhenAllReady(ReadTemperature(), ReadHumidity()); // параллельно
    co_return t.Result() * 100 + h.Result();
}
{code}

Взят из a139. Ошибки воспроизведены на его же коде: планировщик выполнил 33 из 100 одновременно поставленных корутин (переполнение очереди на 32 места возвращалось в список не той стороной); {{join()}} не ждал единственную оставшуюся работу и возобновлял ожидающего дважды; {{task.hpp}} не линковался из двух единиц трансляции; перемещающее присваивание теряло кадр корутины; очереди не уничтожали оставшееся. Внешнее ревью добавило раунды в {{Run()}}, защиту {{AsyncScope}} и проверки {{Resume()}}/{{Result()}}. Кадры корутин выделяются в куче; нужен compare-and-swap (Cortex-M3 и новее). На устройстве не запускался.

h3. События ({{events}})

h4. event-manager

{{hwlib::events::EventManager<Payload, Queue, MaxSubscriptions>}} — публикация и подписка поверх очереди. Обработчики регистрируются по идентификатору события, доставка идёт в том контексте, который вызвал {{Dispatch()}} (блокирующий) или {{TryDispatch()}} (неблокирующий, для потребителей со своим циклом).

Очередь компоненту не принадлежит, её даёт потребитель: на устройстве это примитив RTOS, в тестах — массив. Реализация удовлетворяет концепту {{hwlib::events::EventQueueLike}} — {{TryPush}} (не блокирует, вызывается из прерывания), {{TryPop}}, {{PopBlocking}}. Требование trivially copyable payload принадлежит очереди, которая копирует событие побайтно, а не самому компоненту.

Время передаётся снаружи параметром {{nowMs}}, часов компонент не читает. Переполнение таблицы подписок и переполнение очереди не пишутся в лог, а сообщаются колбэками: компонент, который логирует, вынужден выбрать backend и перестаёт быть независимым от платформы. Отчёт о потерянных событиях копит счётчик и выдаётся не чаще одного раза в {{QUEUE_FULL_REPORT_PERIOD_MS}} — знать о потерях надо, знать о каждой в отдельности не надо, а незадросселированный отчёт замедляет и без того отстающий цикл.

{code:language=cpp}
#include <hwlib/events/event_manager.hpp>

MsgqEventQueue<AppPayload, 8> queue;              // адаптер проекта поверх k_msgq
hwlib::events::EventManager<AppPayload, decltype(queue)> events{ queue };

events.Subscribe(AppEvent::eTick, [](const AppPayload& payload) { OnTick(payload); });
events.SetOnEventsDropped([](std::uint8_t id, std::uint32_t dropped) {
    LOG_WRN("queue full, %u dropped (last id=%u)", dropped, id);
});

std::ignore = events.Push(AppEvent::eTick, payload, k_uptime_get_32());
while (events.TryDispatch()) {}
{code}

h4. button-event

{{hwlib::events::ButtonEventCore}} — антидребезг одной кнопки и разбор нажатия: короткое, длинное или слишком короткое, чтобы что-то значить. Пин, таймеры и часы снаружи: ядро получает фронт с пина, уровень, снятый после выдержки, и срабатывание длинного таймаута, а возвращает {{ButtonAction}} — что сделать с таймерами. Возврат помечен атрибутом {{nodiscard}}: проигнорированный {{ButtonAction}} — это незаведённый таймер, то есть кнопка, которая молчит.

Три времени задают смысл нажатия. Фронт опрашивается один раз, после {{confirmMs}} тишины на линии. Подтверждённое нажатие короче {{minPressMs}} — это касание, а не решение, и оно не сообщается вовсе. Нажатие, всё ещё удерживаемое через {{longPressMs}}, — длинное, и на отпускании оно не сообщается ещё раз как короткое: одно нажатие — одно решение. Без колбэка длинного нажатия таймер не заводится совсем.

Все три входа должны вызываться из одного контекста. На устройстве и фронт с пина, и длинный таймаут приходят в прерывании, поэтому адаптер откладывает их в очередь работ, а не зовёт напрямую, — именно это позволяет держать состояние обычными {{bool}} и делать в колбэках настоящую работу.

{code:language=cpp}
#include <hwlib/events/button_event.hpp>

hwlib::events::ButtonEventCore button{ { .confirmMs = 20, .minPressMs = 200, .longPressMs = 1000 } };
button.SetOnShortPress([] { ToggleView(); });
button.SetOnLongPress([] { EnterService(); });

// в адаптере проекта:
Apply(button.OnEdge());                             // из ISR — только перезапуск выдержки
Apply(button.OnConfirmed(pin.Get(), k_uptime_get())); // из очереди работ
Apply(button.OnLongPressElapsed(pin.Get()));          // из очереди работ
{code}

h3. Хранение ({{persistence}})

h4. settings-record

Запись настроек с контрольной суммой: {{WriteSettingsRecord}} кладёт в хранилище payload вместе с CRC-32, {{ReadSettingsRecord}} отдаёт его обратно, только если сумма сошлась, и не трогает переданную переменную, если нет, — значение по умолчанию переживает и первую загрузку, и испорченную ячейку.

Хранилище даёт потребитель: на устройстве это NVS или драйвер EEPROM, в тестах — словарь. Оно удовлетворяет концепту {{hwlib::persistence::RecordStorageLike}} — {{Write}} и {{Read}} поверх {{std::span}}. Имя раздела и флеш-устройство остаются в проекте, в библиотеку переходит только формат записи.

Зачем сумма: хранилище — не канал. Недописанная после пропадания питания запись или деградировавшая ячейка читаются как правдоподобное значение нужного размера, само чтение при этом не падает. Контрольная сумма — единственное, что отличает это от настройки, которую устройство действительно сохранило.

Payload хранится сырыми байтами, поэтому обязан быть trivially copyable — это {{static_assert}}, а не комментарий.

Зависит от компонента {{crc}}.

{code:language=cpp}
#include <hwlib/persistence/settings_record.hpp>

struct Calibration
{
    std::uint32_t offset{};
    float scale{};
};

if (!hwlib::persistence::WriteSettingsRecord(storage, CALIBRATION_ID, calibration))
{
    LOG_ERR("calibration not saved");
}

Calibration calibration{ DEFAULT_CALIBRATION };
std::ignore = hwlib::persistence::ReadSettingsRecord(storage, CALIBRATION_ID, calibration);
{code}

h4. littlefs-cpp

Обёртка над littlefs: файловая система поверх любого блочного устройства с {{Read}}/{{Write}}/{{Erase}} (и {{Sync}}, если он есть), все буферы внутри объекта, файл, который закрывается сам. Сама littlefs в компонент не входит: её цель CMake даёт проект, имя задаётся {{HWLIB_LITTLEFS_TARGET}}. Проверено на littlefs v2.10.1.

* Монтирование ничего не стирает по своей инициативе. {{Mount()}} только монтирует; {{MountOrFormat()}} форматирует лишь при {{LFS_ERR_CORRUPT}} — так littlefs отвечает на чистую флеш при первом запуске. Любая другая ошибка, в том числе ошибка ввода-вывода, возвращается, и данные остаются на месте.
* Память не выделяется: буферы файловой системы — её члены, файл несёт свой кеш и открывается через {{lfs_file_opencfg}}. Компонент собирается и тестируется с {{LFS_NO_MALLOC}}.
* Файл нельзя ни скопировать, ни переместить: littlefs хранит указатель на каждый открытый файл. Закрывается в деструкторе; повторное закрытие — ошибка, а не второе закрытие.
* Пути копируются в буфер с завершающим нулём: {{std::string_view}} не обязан быть завершён нулём, а littlefs принимает C-строки.
* {{ForEach}} закрывает каталог на любом выходе, {{FileCount}} построен на нём.

{code:language=cpp}
#include <hwlib/persistence/littlefs.hpp>

hwlib::persistence::Littlefs<Flash> fs{ flash, { .blockSize = 4096U, .blockCount = 32U } };
if (const int err = fs.MountOrFormat(); err != LFS_ERR_OK)
{
    LOG_ERR("filesystem: %s", hwlib::persistence::LittlefsErrorName(err).data());
}

hwlib::persistence::Littlefs<Flash>::File file{ fs };
if (file.Open("/ring/0001", LFS_O_WRONLY | LFS_O_CREAT | LFS_O_APPEND) == LFS_ERR_OK)
{
    std::ignore = file.Write(record);
}   // закрыт — и записан — здесь
{code}

h4. boot-slots

Логика A/B-бутлоадера: два слота прошивки, какой из них запускать, как по ним движется обновление, и журнал этого состояния во флеше. Единственный компонент на C (C11): бутлоадеры часто пишутся на C, а C API вызывается и из C++ (заголовки обёрнуты в {{extern "C"}}). Нет кучи, глобального состояния и платформенных заголовков — всё, что касается железа, приходит через колбэки проекта.

* *Решение при загрузке.* {{hwlib_boot_prepare}} только преобразует состояние и говорит, что делать: запустить слот, сохранить и перезагрузиться или остановиться. Новый образ получает один пробный запуск; если он не вызвал {{hwlib_update_confirm}} до следующей перезагрузки — упал, завис, потерял питание, — следующая загрузка отклоняет его и запускает другой слот. Предыдущий подтверждённый образ хранится как резервный для отката.
* *Переходы при обновлении.* {{hwlib_update_begin}}, {{_stage}}, {{_reject}}, {{_rollback}}, {{_confirm}} возвращают {{HWLIB_UPDATE_OK}} или причину отказа и не трогают состояние при отказе.
* *Журнал во флеше.* Каждое изменение дописывается новой 20-байтной записью: сначала тело с CRC, последним — commit-слово, поэтому запись, оборванная пропаданием питания, не действует, а предыдущая остаётся в силе. {{hwlib_boot_journal_load}} различает пустой журнал (первая загрузка), ошибку чтения (состояние неизвестно — не запускать и не сохранять) и журнал без целых записей (состояние потеряно — восстановиться через заводское). Единственное окно, которое один сектор закрыть не может, — пропадание питания между стиранием заполненного сектора и commit восстановленной записи; оно описано и закреплено тестами.
* *Проверка образа.* {{hwlib_image_check}} проверяет заголовок (signature, версия структуры, семейство устройства — решает колбэк проекта, CRC заголовка), размер относительно слота — до чтения тела — и CRC тела блоками по 512 байт с колбэком для watchdog. Возвращает причину отказа, чтобы бутлоадер мог её залогировать.
* *CRC* — CRC-32/ISO-HDLC через колбэки {{reset}} / {{add}} / {{value}}: можно подключить аппаратный блок CRC, программная реализация есть в компоненте.
* *Форматы* записи журнала и заголовка образа байт в байт совпадают с a184 и его {{tools/build_firmware.py}}, так что устройство переходит на компонент без миграции данных.
* Переход на прошивку, reset, watchdog, лог и адреса слотов остаются в проекте. Проверка таблицы векторов Cortex-M ({{hwlib_cortex_m_vector_is_valid}}) вынесена в отдельный заголовок — это чистая арифметика, но правило архитектурное.

Зависимостей нет. Проект без CMake (Keil, IAR) добавляет в сборку пять файлов из {{src/}} и каталог {{include/}}. В проекте с MISRA C (как a184) нужны свои подавления правила 15.5 — в журнале и проверке образа несколько {{return}}; анализ cppcheck с MISRA на компоненте ещё не запускался.

{code:language=c}
#include "hwlib/persistence/boot_journal.h"
#include "hwlib/persistence/boot_slots.h"

hwlib_boot_state_t state;
switch (hwlib_boot_journal_load(&journal, &state))
{
    case HWLIB_BOOT_JOURNAL_OK:
        break;
    case HWLIB_BOOT_JOURNAL_EMPTY:           /* первая загрузка */
    case HWLIB_BOOT_JOURNAL_NO_VALID_RECORD: /* состояние потеряно: оба слота на пробу */
        hwlib_boot_state_init(&state);
        break;
    default:                                 /* READ_ERROR: не запускать и не сохранять */
        panic();
        break;
}

const hwlib_boot_action_t action = hwlib_boot_prepare(&state, check_slot, NULL);
if ((action == HWLIB_BOOT_PANIC) || !hwlib_boot_journal_save(&journal, &state))
{
    panic();
}
if (action == HWLIB_BOOT_RESET)
{
    NVIC_SystemReset();
}
jump_to_slot(state.selected_slot);
{code}

h3. Связь ({{communication}})

h4. transaction-engine

Транзакционный протокол поверх ненадёжного канала: отправка с подтверждением, повторы с экспоненциальным backoff, дедупликация на приёме. Поставляется одним компонентом — части протокола версионируются вместе.

{code:language=cpp}
#include <hwlib/communication/transaction_engine.hpp>
{code}

h5. Формат кадра

{{hwlib::communication::TransactionFrame}}: идентификатор транзакции, тип, метка времени, полезная нагрузка до 64 байт, контрольная сумма CRC-16/CCITT-FALSE из компонента {{crc}}. {{EncodeTransactionFrame}} возвращает число записанных байт либо 0, если нагрузка велика или буфер мал. {{DecodeTransactionFrame}} возвращает {{false}} при несовпадении суммы, обрезанном кадре или несогласованной длине.

h5. Канал

{{hwlib::communication::ITransactionTransport}} — интерфейс, через который протокол отправляет и принимает сырые байты. Что под ним — Zigbee, BLE, UART — протокол не знает. Отправитель и приёмник регистрируют обработчики по отдельности, и каждый принятый кадр доставляется обоим: демультиплексирование не нужно, потому что каждая сторона игнорирует чужие кадры.

h5. Отправитель

{{hwlib::communication::ReliableEventSenderCore<MAX_IN_FLIGHT>}} — назначает идентификатор транзакции, ждёт подтверждения, повторяет с экспоненциальным backoff, паркует отправку, пока канал недоступен, и сообщает об окончательной неудаче.

Время передаётся снаружи параметром {{nowMs}}, а не читается внутри, поэтому машина состояний тестируется на хосте с поддельными часами. Число попыток включает первую отправку: при {{maxRetry = 4}} уходит ровно четыре кадра, а не пять.

{code:language=cpp}
hwlib::communication::ReliableEventSenderCore<2> sender{deviceId, sendFn};
sender.SetOnConfirmed([](std::uint32_t txnId) { MarkDone(txnId); });
sender.SetOnFailed([](std::uint32_t txnId) { MarkFailed(txnId); });
const auto txnId = sender.Submit(commandType, payload, nowMs);
{code}

h5. Приёмник

{{hwlib::communication::ReliableEventReceiverCore<DEDUP_CAPACITY>}} — проверяет кадр, отбрасывает повтор уже обработанной транзакции, передаёт новую в обработчик и всегда отвечает подтверждением с тем же идентификатором. Повтор подтверждается, но второй раз не обрабатывается: иначе потерянное подтверждение приводило бы к двойному выполнению команды.

{code:language=cpp}
hwlib::communication::ReliableEventReceiverCore<16> receiver{handlerFn, sendAckFn};
receiver.OnFrameReceived(rawBytes);
{code}

h4. mqtt-topic

{{hwlib::communication::MatchTopic}} — соответствует ли фильтр подписки MQTT имени топика, по разделу 4.7 спецификации MQTT 3.1.1 (в 5.0 не менялся). Фильтр разбирается по уровням, от {{/}} до {{/}}:

* {{+}} соответствует ровно одному уровню, в том числе пустому;
* {{#}} соответствует своему уровню, всем уровням ниже и родительскому — {{sport/#}} соответствует {{sport}};
* ни один из них не соответствует топику, начинающемуся с {{$}}, с первого уровня — {{#}} не отдаёт {{$SYS/...}} клиенту, который не подписался на него явно.

Символ подстановки считается таковым, только когда он занимает весь уровень. {{#}} не на последнем уровне делает фильтр недействительным, и такой фильтр не соответствует ничему. Функция {{constexpr}}.

{code:language=cpp}
#include <hwlib/communication/mqtt_topic.hpp>

static_assert(hwlib::communication::MatchTopic("home/+/temp", "home/kitchen/temp"));
if (hwlib::communication::MatchTopic(subscription.filter, message.topic))
{
    subscription.handler(message);
}
{code}

h4. can-filter-codec

{{EncodeCanFilters}} и {{DecodeCanFilters}} переводят список фильтров приёма CAN в байты и обратно — для передачи по BLE, UART или любому другому каналу. Фильтр {{hwlib::communication::CanFilter}} имеет поля Zephyr {{struct can_filter}}: {{id}}, {{mask}} (кадр проходит, если {{(frameId & mask) == (id & mask)}}) и {{flags}}, которые кодек переносит, не разбирая.

Формат совпадает с форматом a138 байт в байт: версия {{0x01}}, число фильтров, затем на каждый фильтр запись {{0x01 0x08}} с id и mask (по 4 байта little-endian) и запись {{0x02 0x01}} с флагами — {{EncodedCanFiltersSize(N)}} = 2 + 13·N байт. Декодер сопоставляет записи по порядку, а не по позиции, и пропускает записи с незнакомым тегом, поэтому следующая версия формата может добавлять поля.

Отказ — {{0}} у {{Encode}}, пустой {{std::optional}} у {{Decode}}, выходной буфер не тронут: не хватает места, больше 255 фильтров, id или mask шире 29 бит, другая версия, запись обрезана или у фильтра нет записи флагов. Входной и выходной буферы не должны перекрываться. Функции {{constexpr}}, без выделения памяти.

{code:language=cpp}
#include <hwlib/communication/can_filter_codec.hpp>

std::array<hwlib::communication::CanFilter, MAX_FILTERS> filters{};
if (const auto count = hwlib::communication::DecodeCanFilters(written, filters); count.has_value())
{
    for (const auto& f : std::span{filters}.first(*count))
    {
        const can_filter zephyr{.id = f.id, .mask = f.mask, .flags = f.flags};
        ...
    }
}
{code}

h4. zigbee-app

Тонкий прикладной слой над ZBOSS, Zigbee-стеком nRF Connect SDK: эндпоинты, вход в сеть и выход из неё, сон и опрос End Device, обработка сигналов стека. Состоит из двух частей:

* ядро — {{DecideZigbeeSignal}} (что делать с каждым сигналом), {{ZigbeeSleepGate}} и {{ZigbeeEndpointRegistry}} — заголовки без ZBOSS, собираются где угодно и покрыты тестами;
* адаптер {{hwlib::communication::ZigbeeApp}} вызывает ZBOSS и собирается, только если SDK даёт цели {{zboss}} и {{zigbee}}. Если {{CONFIG_ZIGBEE}} включён, а целей нет, конфигурация останавливается с ошибкой.

Обработчик сигналов стека {{zboss_signal_handler}} определяет приложение и передаёт сигнал в {{HandleSignal()}}. Роль следует из сборки: {{CONFIG_ZIGBEE_ROLE_END_DEVICE}} — спящий End Device, иначе роутер. Интервалы опроса End Device задаются в {{ZigbeePollConfig}}, в миллисекундах. Вызовы, которые только планируют работу в поток ZBOSS, безопасны из потоков и прерываний; {{CancelJoining()}} и {{TriggerLeave()}} — только из потока, потому что берут мьютекс стека.

{code:language=cpp}
#include <hwlib/communication/zigbee_app.hpp>

hwlib::communication::ZigbeeApp g_zigbee{FW_VERSION_STRING};

extern "C" void zboss_signal_handler(zb_bufid_t bufid)
{
    g_zigbee.HandleSignal(bufid);
}

int main()
{
    std::ignore = g_zigbee.AddEndpoint(g_sensorEndpoint);
    g_zigbee.SetCanSleepCallback([] { return !g_busy; });
    g_zigbee.Start();
}
{code}

При переносе из a174 найдена ошибка единиц: окно turbo poll передавалось в интервалах маяка вместо миллисекунд и длилось около 330 мс вместо 5 с. Компонент передаёт миллисекунды, поэтому при переходе на него окно станет настоящим — нагрузку на CPU стоит измерить. Адаптер собран в образе nRF Connect SDK для End Device и роутера; линковка в прошивку и запуск на устройстве не проверялись.

h3. Драйверы ({{drivers}})

Драйвер получает шину как параметр шаблона: подходит любой тип с методами, которые называет concept драйвера. Поэтому в драйвере нет кода платформы — адаптер к своему HAL (Zephyr, Harmony, GD32 SPL) проект пишет сам, обычно в несколько строк. Concept шины общий для всех I2C-драйверов и лежит в компоненте {{i2c-bus}}; драйвер требует только те передачи, которые делает. Для SPI-драйверов то же даёт {{spi-bus}}.

h4. i2c-bus

Concept шины I2C — по одному на передачу: {{I2cWrite}} ({{Write(address, tx)}}), {{I2cRead}} ({{Read(address, rx)}}), {{I2cWriteRead}} ({{WriteRead(address, tx, rx)}} с повторным START — чтение регистра) и {{I2cBus}} = запись + чтение регистра. Адрес 7-битный, каждая функция возвращает {{bool}} — подтвердило ли устройство; шина, возвращающая код ошибки, concept не удовлетворяет намеренно: какой код считать успехом, решает адаптер. В {{hwlib/drivers/testing/fake_i2c_bus.hpp}} — {{FakeI2cBus}} для тестов драйверов на хосте: ответы по сценарию, запись всех передач, отказы по запросу.

{code:language=cpp}
struct ZephyrI2c
{
    const device* dev;
    bool Write(std::uint8_t a, std::span<const std::uint8_t> tx) { return i2c_write(dev, tx.data(), tx.size(), a) == 0; }
    bool Read(std::uint8_t a, std::span<std::uint8_t> rx) { return i2c_read(dev, rx.data(), rx.size(), a) == 0; }
    bool WriteRead(std::uint8_t a, std::span<const std::uint8_t> tx, std::span<std::uint8_t> rx)
    {
        return i2c_write_read(dev, a, tx.data(), tx.size(), rx.data(), rx.size()) == 0;
    }
};
static_assert(hwlib::drivers::I2cBus<ZephyrI2c> && hwlib::drivers::I2cRead<ZephyrI2c>);
{code}

{{RecoverI2cBus(pins, halfPeriod)}} ({{hwlib/drivers/i2c_bus_recovery.hpp}}) — очистка шины по UM10204, 3.1.16: устройство, оставленное сбросом МК посреди байта, держит SDA в нуле, и шина занята навсегда. Функция отпускает обе линии и даёт до девяти тактов SCL, каждый заканчивается попыткой STOP — как {{i2c_generic_scl_recovery()}} в Linux, — и возвращает {{eFree}}, {{eRecovered}}, {{eSdaHeld}} или {{eSclHeld}}. Выводы — GPIO с открытым стоком через concept {{I2cRecoveryPins}}, ожидание полупериода (от 5 мкс) — callable вызывающего. Вызывающий должен единолично владеть шиной: периферия I2C выключена, IRQ и DMA молчат, других мастеров нет. Взято из a159-bpu-firmware ({{i2cCtrl::SwBusReset()}}): там при неотпускающейся SDA функция возвращала успех, а STOP не выдавался вовсе — функции выводов были названы наоборот. На железе не запускалось.

h4. stc3100

{{hwlib::drivers::Stc3100<Bus>}} — драйвер монитора батареи ST STC3100: кулоновский счётчик на внешнем шунте, напряжение батареи, температура кристалла и 32 байта RAM, которые сохраняются при сбросе МК. Шина должна удовлетворять concept {{I2cBus}} из {{i2c-bus}}: {{Write(address, tx)}} и {{WriteRead(address, tx, rx)}}, адрес 7-битный, оба возвращают {{bool}}. Таймауты и восстановление шины — забота шины.

Каждое чтение — одна транзакция I2C (два байта значения согласованы, как требует даташит) и возвращает {{std::optional}}: при ошибке значения нет. Единицы целые: мВ, мкА, мкА·ч, м°C; сопротивление шунта в мОм — параметр конструктора. Драйвер ничего не ждёт: первое измерение тока — до 500 мс после {{Start()}}, напряжение и температура обновляются раз в 4 с, их нужно опрашивать. Запись в {{REG_CTRL}} всегда оставляет вывод IO0 открытым.

{code:language=cpp}
#include <hwlib/drivers/stc3100.hpp>

struct ZephyrI2c
{
    const device* dev;
    bool Write(std::uint8_t a, std::span<const std::uint8_t> tx) { return i2c_write(dev, tx.data(), tx.size(), a) == 0; }
    bool WriteRead(std::uint8_t a, std::span<const std::uint8_t> tx, std::span<std::uint8_t> rx)
    {
        return i2c_write_read(dev, a, tx.data(), tx.size(), rx.data(), rx.size()) == 0;
    }
};

ZephyrI2c g_i2c{DEVICE_DT_GET(DT_NODELABEL(i2c1))};
hwlib::drivers::Stc3100<ZephyrI2c> g_gauge{g_i2c, 33U}; // шунт, мОм

// Счётчик продолжает считать, пока МК перезагружается: обнулять его только при холодном старте.
const auto running = g_gauge.IsRunning();
if (g_gauge.Probe() && running.has_value() && !*running)
{
    std::ignore = g_gauge.ResetCharge() && g_gauge.Start();
}
const auto mv = g_gauge.ReadVoltageMv();
{code}

Взят из a160; при переносе исправлено, что сброс заряда прижимал вывод IO0 к земле (то же в a156 и a159), инициализация без ограничения ждала напряжения, а неудачное чтение возвращало ноль вместо ошибки. С реальным чипом драйвер не запускался. Алгоритм оценки заряда ({{BatteryMonitor}} из a156, a159, a160) — отдельная задача.

h4. sht40

{{hwlib::drivers::Sht40<Bus>}} — драйвер датчика влажности и температуры Sensirion SHT40 (семейство SHT4x по адресам 0x44, 0x45, 0x46). Шине нужны {{I2cWrite}} и {{I2cRead}}: датчик отвечает на заголовок чтения без адреса регистра. Драйвер ничего не ждёт: измерение — это команда {{StartMeasurement(precision)}}, ожидание {{MeasurementTime(precision)}} (8,3 / 4,5 / 1,6 мс — максимум по даташиту), которое вызывающий тратит как хочет, и {{ReadMeasurement()}}. Результат — температура в м°C и влажность в м%RH, обрезанная до 0…100 %RH, целочисленно, с округлением до ближайшего; чтение различает «нет ответа» (датчика нет, ещё измеряет или данные уже прочитаны — выдаются один раз) и несовпадение CRC.

{code:language=cpp}
Task<std::optional<Sht40Measurement>> Measure(Io& io, Sht40<ZephyrI2c>& sensor)
{
    if (!sensor.StartMeasurement(Sht40Precision::eMedium))
    {
        co_return std::nullopt;
    }
    co_await io.ScheduleAfter(Sht40<ZephyrI2c>::MeasurementTime(Sht40Precision::eMedium));
    const auto result = sensor.ReadMeasurement();
    co_return result.HasValue() ? std::optional{result.value} : std::nullopt;
}
{code}

Взят из двух драйверов a138 и сверен с даташитом SHT4x 6.5. Исправлено: в a138-ble-gateway чтение с неверным CRC возвращалось как 0 °C и 0 %RH, в драйвер была зашита поправка продукта −3 °C, влажность не обрезалась, ошибки шли исключениями; в a138-ble-sensors расчёт шёл в {{double}} (программно на Cortex-M4F), неудачный сброс в конструкторе выключал драйвер навсегда, 0.0 при ошибке не отличался от настоящих 0 °C, отрицательная температура печаталась как «-3.-45». Оба ждали внутри драйвера. С реальным датчиком не запускался.

h4. adxl345

{{hwlib::drivers::Adxl345<Bus>}} — драйвер трёхосевого акселерометра Analog Devices ADXL345 по I2C (адрес 0x53 или 0x1D). {{Configure(config)}} переводит чип в standby, выключает выходы прерываний, пишет частоту (0,1–3200 Гц), режим пониженного потребления, диапазон ±2…16 g, полное или 10-битное разрешение и вывод DATA_READY, включает измерение и сверяет регистры, обходя INT_SOURCE, чтобы не стереть события приложения; {{false}} — конфигурация не действует, состояние чипа неизвестно. {{ReadSample()}} читает три оси одной передачей, {{IsDataReady()}} — флаг DATA_READY, {{ToMilliG()}} переводит отсчёт в mg целочисленно. FIFO, tap, activity, free-fall, sleep, смещения, self-test и SPI не поддержаны.

Взят из a159-bpu-firmware ({{sensor_manager/adxl345}}). Исправлено: результаты записей конфигурации игнорировались; при таймауте чтения оставался прошлый отсчёт; таймауты по {{_CP0_GET_COUNT()}} ломались на переполнении; чип, переживший сброс МК, перенастраивался без standby. С реальным чипом не запускался.

h4. spi-bus

Concept устройства на шине SPI: {{SpiDevice}} = {{bool Transfer(tx, rx)}} — одна полнодуплексная передача с выбранным чипом; {{rx}} либо пустой (запись), либо той же длины, что {{tx}}: байт i принимается, пока уходит байт i. Chip select, режим, частота и блокировка общей шины — забота адаптера, как у {{spi_dt_spec}} в Zephyr. {{true}} значит «передача состоялась»: подтверждения в SPI нет, отсутствие чипа драйвер распознаёт сам (по регистру версии, CRC). В {{hwlib/drivers/testing/fake_spi_device.hpp}} — {{FakeSpiDevice}}: ответы по сценарию, запись передач, отказы по запросу и отказ на передачу, нарушающую правило длины.

{{SpiBus}} (с 0.1.1) — для протоколов, где транзакция не одна передача: драйвер сам вызывает {{Select()}} и {{Deselect()}}, {{Transfer(tx, rx)}} CS не трогает, {{SetClockHz(hz)}} меняет частоту. С поднятым CS можно тактировать байтами {{FFh}} — их не примет ни один чип. {{FakeSpiBus}} записывает все действия по порядку.

h4. sd-spi

{{hwlib::drivers::SdSpi<Bus>}} — драйвер SD-карты в режиме SPI поверх {{SpiBus}}: SDSC (байтовая адресация), SDHC и SDXC (блочная), MMC v3 до 2 ГБ. Драйвер ничего не ждёт: {{StartInit()}}/{{PollInit()}} (CMD0, CMD8, CMD59, ACMD41 или CMD1, OCR, CSD), {{StartRead()}}/{{PollRead()}} и {{StartWrite()}}/{{PollWrite()}} по сектору 512 байт, {{StartErase()}}/{{PollErase()}}, {{Cancel()}} для брошенной операции. CRC включён: CRC7 у каждой команды, CRC16 у каждого блока в обе стороны. Ёмкость — 64-битная, C_SIZE CSD v2 — все 22 бита. Ответ читается по байту до R1, так что маркер данных, пришедший сразу, не теряется; перед каждой командой проверяется, что карта отпустила DO, иначе {{eBusy}}. Ограничивать опросы по времени — забота вызывающего. Многоблочные CMD18/CMD25 не поддерживаются.

Заменяет производное от ChaN {{mmc.c}} в a159-bpu-firmware ({{sd_card_fifo/sd_card}}). Исправлено: ёмкость считалась в 32 битах (карты от 4 ГиБ); у CSD v2 терялись старшие биты C_SIZE (SDXC больше 32 ГиБ); при стирании SDSC передавались номера секторов вместо байтовых адресов, таймаут 1 с на всю карту; CRC блоков отбрасывался, CRC команд был фиктивным; буфер читался через {{reinterpret_cast}} к {{uint32_t}}. Драйвер написан другим агентом по заданию и прошёл три раунда ревью. С реальной картой не запускался.

h4. mfrc522

{{hwlib::drivers::Mfrc522<Spi>}} — драйвер NFC-считывателя NXP MFRC522 для карт ISO/IEC 14443 A на 106 кБод: читает UID (4, 7 или 10 байт), SAK и ATQA. Драйвер ничего не ждёт: каждая операция — {{Start…()}} и {{Poll…()}}, который отвечает {{ePending}}, пока она не закончилась. Запуск чипа: {{SoftReset()}}, опрос {{IsReady()}}, {{Configure()}} (возвращает версию или {{eNoChip}}); чтение карты — {{StartActivation()}} / {{PollActivation()}}, усыпление — {{StartHalt()}} / {{PollHalt()}}. Ошибки различаются: нет ответа, коллизия двух карт, неверный BCC или CRC_A, ошибка приёма, перегрев, шина. Протокол без чипа — {{Iso14443aActivation}} и {{Iso14443aCrc}} в {{iso14443a.hpp}}.

*Число опросов ограничивает вызывающий*: когда никто не отвечает, обмен заканчивает таймер чипа (25 мс), но ответ, который начался и оборвался, чип сам не завершит; после своего дедлайна достаточно вызвать {{Start…()}} снова.

{code:language=cpp}
Task<std::optional<Iso14443aCard>> ReadCard(Io& io, Mfrc522<ZephyrSpi>& reader)
{
    if (!reader.StartActivation())
    {
        co_return std::nullopt;
    }
    for (int poll = 0; poll < MAX_POLLS; ++poll)
    {
        const auto card = reader.PollActivation();
        if (card.error != Mfrc522Error::ePending)
        {
            co_return card.HasValue() ? std::optional{card.value} : std::nullopt;
        }
        co_await io.ScheduleAfter(1ms);
    }
    co_return std::nullopt;
}
{code}

Взят из a174-hardware и сверен с даташитом MFRC522 Rev. 3.9 и ISO/IEC 14443-3. Исправлено: SAK принимался без проверки CRC_A (один сбитый бит каскада менял длину UID), коллизия двух карт не считалась ошибкой, любой ответ на HLTA считался успешной остановкой, длину UID решал байт 88h, а не SAK; драйвер ждал внутри себя и считал CRC сопроцессором чипа. Слой с рабочей очередью Zephyr и колбэком не переносился — в нём была гонка на {{std::function}}. Побитовая антиколлизия не реализована: с двумя картами в поле — {{eCollision}}. С реальным чипом не запускался.

h4. ad7797

{{hwlib::drivers::Ad7797<Spi>}} — драйвер 24-битного сигма-дельта АЦП Analog Devices AD7797 со встроенным усилителем ×128 для тензомостов: весов и тензодатчиков. Драйвер ничего не ждёт: {{StartConversion()}}, ожидание {{ConversionTime(rate)}} (1 мс запуск генератора плюс время установления фильтра, 121 мс на 16,7 Гц) и {{PollConversion()}}, который отвечает {{ePending}}, пока результата нет. Готовность читается из регистра статуса, поэтому CS не нужно держать низким всё преобразование. Результат — код со знаком относительно нулевого входа (в биполярном режиме 800000h — ноль); {{ToMicrovolts()}} переводит его в мкВ целочисленно, без деления. Перегрузка входа — ошибка {{eOverrange}}, отсутствующий чип — {{eNoChip}}, в том числе когда MISO висит в 1 или в 0. Граммы — забота приложения: тара и калибровка по известному грузу.

Взят из a146-control-board и сверен с даташитом AD7796/AD7797 Rev. B. Исправлено: напряжение считалось с расширением знака смещённого двоичного кода (+полная шкала давала −VREF/128), в регистр веса Modbus уходил сырой код × 10 в {{uint16_t}} (переполнение, UB), бит ERR игнорировался, {{SelectBurnout()}} портил бит полярности, ожидания без конца. С реальным чипом не запускался.

h4. max31856

{{hwlib::drivers::Max31856<Spi>}} — драйвер АЦП термопары MAX31856 с компенсацией холодного спая и линеаризацией для типов B, E, J, K, N, R, S и T. {{StartConversion()}} запускает одно преобразование, {{PollConversion()}} отвечает {{ePending}}, пока бит 1SHOT не сбросится (вывод DRDY не нужен), затем отдаёт температуру термопары и холодного спая в м°C и биты отказов. При любом отказе — {{eFault}}, значения тоже отдаются, но им нельзя верить: оборванная термопара показывает что угодно. Конфигурация сверяется при каждом опросе — так распознаётся отсутствующий чип и чип, сбросивший настройки после просадки питания. {{ConversionTime(config)}} — максимум по даташиту с учётом усреднения и проверки обрыва.

Взят из a146-control-board и сверен с даташитом MAX31856 Rev 0. Исправлено: отказы проверялись только при старте (термопара, оборвавшаяся позже, выдавала мусор как температуру), отсутствующий чип только проверялся {{assert}}, сброс отказов не действовал в режиме компаратора. Замечено и не перенесено: формула напряжения термопары типа K для Modbus ошибалась примерно на 1,1 мВ (около 27 °C). С реальным чипом не запускался.

h4. linear-actuator

{{hwlib::drivers::LinearActuator<Bridge>}} ведёт линейный актуатор — коллекторный мотор через H-мост ({{Extend}}, {{Retract}}, {{Brake}}), потенциометр положения, датчик тока — в одну из N равноотстоящих позиций между упорами. Без FreeRTOS, таймеров и потоков: {{Update(nowMs, positionCode, currentCode)}} вызывается раз в 10–100 мс и сам управляет мостом. {{Calibrate()}} находит оба упора и заодно узнаёт, в какую сторону растёт код датчика. Отказы: перегрузка по току, заклинивание при движении, калибровка, не успевшая за таймаут, отсутствие хода.

{code:language=cpp}
constexpr LinearActuatorConfig DAMPER{.positions = 10, .tolerance = 10, .maxCurrent = 3910};
LinearActuator<Bridge> g_damper{g_bridge, DAMPER};

std::ignore = g_damper.Calibrate();
for (;;)
{
    g_damper.Update(NowMs(), ReadPositionAdc(), ReadCurrentAdc());
    SleepMs(10);
}
{code}

Взят из a146-control-board ({{actuator-ctrl}}). Исправлено: таблица позиций индексировалась после одного {{reserve()}} (UB), позиции и коды пересчитывались несимметрично, калибровка не имела таймаута, направление датчика предполагалось, таймер FreeRTOS и задача управляли мотором одновременно, четыре актуатора делили одну перезаписываемую ячейку уведомления. На плате не запускался.

h4. fan5646

{{hwlib::drivers::Fan5646<Spi>}} программирует onsemi FAN5646 — драйвер светодиода с плавным нарастанием и спадом — через его однопроводной интерфейс TinyWire, сформированный на линии MOSI: байт SPI на бит, 11111110b — единица, 10000000b — ноль. {{Configure(config)}} записывает все пять регистров одной передачей (ток 5–20 мА, режим Follow/Play/One-Shot, SLOW, два импульса), {{Write()}} — один регистр; время нарастания, включения и паузы — функции {{RampTime}}, {{OnTime}}, {{OffTime}} по формулам даташита. Адаптер SPI должен гарантировать старший бит первым, непрерывную передачу без пауз между байтами и низкий MOSI в покое; частота 500 кГц (пределы 375 кГц … 2 МГц). Запуск паттерна — забота приложения: вывод CTRL переводится в GPIO и держится высоким, и это нужно уложить в 200 мкс. Чип снят с производства.

Взят из a156-dl200p ({{indication/tiny_wire}}), кодирование битов сохранено. Исправлено: {{SendExec()}} ничего не исполнял (держал CTRL низким, а исполнение требует высокого), после каждого слова драйвер спал 200 мкс, отправляя чип в IDLE между регистрами, настройка отправлялась дважды «чтобы дошло». Внешнее ревью проверено и учтено. С реальным чипом не запускался.

h4. mcp4922

{{hwlib::drivers::Mcp4922<Spi>}} — драйвер двухканального 12-битного ЦАП Microchip MCP4922: одна 16-битная команда на кадр CS. {{Write(channel, code, config)}} пишет входной регистр канала (усиление 1x/2x и буфер опорного напряжения задаются при каждой записи), {{WriteBoth(a, b)}} — оба, программное отключение канала — отдельной командой. Коды 0–4095 не обрезаются: недопустимый код отвергается, ничего не отправляя; ограничения схемы после ЦАП — забота приложения. LDAC переносит входные регистры на выходы: притянутый к земле — сразу после записи, поднятый — по импульсу, одновременно для обоих каналов; после {{WriteBoth}} с результатом {{false}} импульс LDAC подавать нельзя. После включения питания выходы в высоком импедансе, пока не будет записи и низкого LDAC.

Взят из a168-waveform-generator ({{lib/mcp4922}}), формат команды сохранён. Исправлено: драйвер молча обрезал каждый код до 3430 — предел 500 мкА выходного каскада той платы, — хотя приложение масштабировало до 4095; ошибка SPI проверялась только {{NRFX_ASSERT}} и в release-сборке терялась. Замечено в приложении и не перенесено: LDAC общий для двух каналов, и прерывание канала A защёлкивает заодно ожидающее значение канала B. С реальным чипом не запускался.

h4. ads129x

{{hwlib::drivers::Ads129x<Spi, N>}} — драйвер TI ADS1294, ADS1296, ADS1298 и их версий R: 4, 6 или 8 каналов 24-битного фронтенда ЭКГ/ЭЭГ по SPI (режим 1), один чип или N чипов в daisy-chain на одном CS. {{Probe()}} читает ID (модель и число каналов), {{Configure(registers)}} останавливает конверсии, пишет регистры модели во все чипы (зарезервированные биты — как требует даташит, регистры отсутствующих каналов ADS1294/6 не трогаются) и сверяет их с первым; {{Start()}}/{{Stop()}} — командами, вывод START держится в нуле. {{ReadFrame()}} читает всю цепочку одной передачей, выравнивает данные через лишний бит между чипами и проверяет заголовок 1100b в слове статуса каждого чипа — так обнаруживается пропавший чип. Команды и кадры можно гнать через два {{SpiDevice}}: медленный (tSDECODE, не выше 2·fCLK) и быстрый (до 20 МГц). Тайминг относительно DRDY, tSCCS и общий CLK цепочки — забота вызывающего и адаптера.

Взят из a159-bpu-firmware ({{sensor_manager/ads1298}}), значения регистров и сборка битов цепочки — как там. Исправлено: результаты записи конфигурации игнорировались и не читались обратно; слово статуса не проверялось; вместе с командой START поднимался вывод START; {{SendStartCmd()}} возвращал результат только второй передачи; лишний такт цепочки выдавался вручную при выключенном SPI. С реальным чипом не запускался.

h2. Подключение к проекту

h3. 1. Добавить нужные компоненты сабмодулями

Подключается только то, чем пользуетесь: неиспользуемые компоненты не скачиваются вовсе.

{code:language=bash}
git submodule add git@github.com:integra-lib/crc.git external/hwlib/crc
git commit -m "build: add integra-lib crc component"
{code}

h3. 2. Подключить в CMake

{code:language=cmake}
add_subdirectory(external/hwlib/crc)
target_link_libraries(app PRIVATE Hwlib::crc)
{code}

Каждый компонент несёт свой каталог включений, поэтому заголовок недоступен, пока компонент не слинкован: забытая зависимость даёт ошибку компиляции, а не случайно работающую сборку.

h3. 3. Включить заголовок

{code:language=cpp}
#include <hwlib/algorithms/crc.hpp>
{code}

h3. Компонент с зависимостями

Зависимости есть у тринадцати компонентов: {{transaction-engine}} нужны {{crc}}, {{bit-ops}} и {{dedup-cache}}, {{settings-record}} — {{crc}}, {{stc3100}}, {{sht40}} и {{adxl345}} — {{i2c-bus}}, {{mfrc522}}, {{ad7797}}, {{max31856}}, {{fan5646}}, {{mcp4922}}, {{ads129x}} и {{sd-spi}} — {{spi-bus}}, а {{littlefs-cpp}} — сама littlefs, сторонняя библиотека, цель CMake для которой даёт проект. Они подключаются *рядом* с зависимым компонентом, а не внутрь него, — тогда в дереве проекта каждый компонент существует ровно в одном экземпляре и две разные версии одного компонента в одну прошивку попасть не могут.

{code:language=cmake}
add_subdirectory(external/hwlib/crc)
add_subdirectory(external/hwlib/bit-ops)
add_subdirectory(external/hwlib/dedup-cache)
add_subdirectory(external/hwlib/transaction-engine)
{code}

Если компонента нет или его версия вне допустимого диапазона, CMake останавливается на configure с сообщением, в котором названы и компонент, и найденная версия:

{noformat}
transaction_engine needs Hwlib::crc >= 0.2.0 and < 0.3.0, found 0.3.0.
{noformat}

h3. Версии

Каждый компонент выпускается независимо и помечается тегом {{vX.Y.Z}}. До версии 1.0 minor-релиз может ломать API — поэтому зависимые компоненты принимают версию в текущем minor-диапазоне 0.2.x.

{code:language=bash}
git -C external/hwlib/crc fetch --tags
git -C external/hwlib/crc checkout v0.2.0
git add external/hwlib/crc
git commit -m "build: bump crc to v0.2.0"
{code}

Обновление версии — обычное изменение в истории проекта: видно в diff, проходит ревью, откатывается коммитом.

h3. Что учесть в CI потребителя

Компоненты — обычные сабмодули, поэтому сборочным job'ам нужен {{GIT_SUBMODULE_STRATEGY: normal}} (или {{recursive}}). Частая ошибка: переменная выставлена только у job'а с unit-тестами, а сборка прошивки падает на отсутствующем каталоге.

h3. Требования

* C++20; {{boot-slots}} — C11 (собирается и как C99)
* исключения и RTTI библиотека не использует и не требует
* динамическая память нужна компоненту {{function}}, а также обработчикам {{event-manager}} и колбэкам {{button-event}} и {{zigbee-app}}: они хранятся в {{std::function}}, которая выделяет память под достаточно большой захват. Регистрируются они один раз при старте, но в контексте, где куча запрещена вовсе, это надо учитывать. {{worker}} выделяет память на каждую поставленную работу — и под очередь, и под {{std::function}}. Кадры корутин {{coro}} выделяются через {{operator new}}, как требует язык: куча нужна и ему
* от конкретного МК компоненты не зависят, кроме адаптера {{zigbee-app}}: он работает только в nRF Connect SDK с ZBOSS. Это проверено сборкой каждого под Cortex-M0 и Cortex-M4F (arm-none-eabi GCC 16), nRF52 (Zephyr SDK GCC 12), ESP32-S3 (GCC 11 и 14) и ESP32-C3 (GCC 11) с {{-fno-exceptions -fno-rtti}}: ни одному не нужны атомарные операции, которых нет у ядра, поддержка потоков в библиотеке C++ или исключения, кроме {{coro}}: его планировщику и счётчикам нужен compare-and-swap, которого нет у Cortex-M0, — там сборка обращается к {{__atomic_*}} из libatomic. На ядрах без FPU вычисления с {{float}} в {{ema-filter}} и в фильтрах с {{float}}-отсчётами эмулируются программно — это вопрос скорости, а не корректности. {{boot-slots}} пока собран только под Cortex-M0 и Cortex-M4 (arm-none-eabi GCC, {{-std=c11}} и {{-std=c99}}, {{-Wconversion -Werror}}), {{can-filter-codec}}, {{stc3100}}, {{battery-monitor}}, {{bresenham-modulator}}, {{i2c-bus}}, {{sht40}}, {{spi-bus}}, {{mfrc522}}, {{ad7797}}, {{max31856}}, {{linear-actuator}}, {{fan5646}}, {{mcp4922}}, {{adxl345}}, {{ads129x}} и {{sd-spi}} — только под Cortex-M0 и Cortex-M4F (arm-none-eabi GCC 16, {{-Wconversion -Werror}}), {{coro}} — только под Cortex-M4F
* {{transaction-engine}}, {{boot-slots}} и адаптер {{zigbee-app}} — компоненты со своими единицами трансляции, то есть статические библиотеки. Под Zephyr такой библиотеке нужно передать флаги SDK, иначе она соберётся с другим ABI, чем приложение. Перед использованием в прошивке это надо проверить на реальном тулчейне; заголовочных компонентов это не касается — они компилируются в составе приложения.

Собственные тесты компонентов собираются, только когда репозиторий компонента открыт как корневой проект. В сборке потребителя они не участвуют, GoogleTest не скачивается.
